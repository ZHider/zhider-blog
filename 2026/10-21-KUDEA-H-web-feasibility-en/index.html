Two Mental Models: VBA and Web

A mental model is the picture in your head of “what this system is.” When a problem comes up, the picture you see first decides how you make decisions. Many decisions in your business plan are made from the VBA picture, and they go off track when applied to the web. Below are the two pictures, then a comparison against specific statements in your plan.

1. The VBA Mental Model

The system in your head is one Excel file.

  • Where the file is, the system is. If the file is on Zhang’s computer, the system is on Zhang’s computer.
  • Double-click the file, and the system starts working. Close the file, and the system stops.
  • The interface (worksheets), the rules (macros), and the data (cells) all live inside this one file.
  • To give it to another center, copy the file over. The two copies are then independent and do not affect each other.
  • Upgrading means sending a new file, and the user overwrites the old one.
  • Backing up means copying the file.
  • If two people open the same file at the same time, they conflict. So usually people take turns, or put it on a shared drive and open it at different times.
  • When something goes wrong, open the file and look.

This picture is simple and direct, and your VBA version succeeded by following it.

2. The Web Mental Model (Best Practice)

The system in your head should be a service that is always running, plus a database.

  • The service runs on a machine that stays on. The program is always running, waiting for users to access it.
  • A user opens a URL in a browser, which means accessing this service. Closing the browser does not stop the service.
  • Data lives in the database, separate from the service program. Every time the program does something, it reads from and writes to the database.
  • Multiple users accessing at the same time is the normal state. The program must handle them simultaneously, and each person’s data must not interfere with others.
  • Upgrading means replacing the program on that machine. The next time users refresh the browser, they see the new version, and the data does not move.
  • Backing up means backing up the database and the attachments, and making sure the records in the database match the files in the attachments folder.
  • When something goes wrong, look at the logs on the server.
  • Someone must always ensure that machine stays on, the program keeps running, the URL is reachable, and backups are being made.

The key point of this picture: the system is something that runs continuously, not a file that only exists when opened.

3. The Same Question, Answered by Two Mental Models

Question VBA mental model Web mental model
Where is the system In a file On a machine that stays on
When does the system exist When the file is open All the time
Where is the data In the file, together with the code In the database, separate from the code

4. Which Statements in Your Plan Still Use the VBA Mental Model

A few statements in your plan need a different way of thinking when moved to the web:

“One program for one center, 50 programs 50 centers.”
This is the copy-the-file thinking from VBA. On the web, 50 centers can be 50 separate services, or 1 service managing 50 centers. These two differ a lot in maintenance workload. Your current statement assumes the first, but your plan has not compared the two.

“In case of need we will connect with the remote machine.”
This is the VBA “go to that machine and open the file” thinking. On the web, troubleshooting usually starts with logs and monitoring, and logging into the server is the last resort, not the daily practice.

“Data is never shared between different centers neither to us by web.”
The requirement is reasonable. But in the web mental model, it translates to: data sits in the server-side database, each center can only see its own data, and you as the operator cannot see it either. That is a tenant-isolation question, not a “where is the data stored” question.

“The web version is just swapping VBA for Python, logic unchanged.”
In the web mental model, business logic goes into the server-side program, data goes into the database, and the interface goes into the browser. These are three separate pieces, unlike VBA where all of it lives in one file.

5. Three Concrete Points of the Mental Shift

  1. From “file” to “service.” The question you ask from now on changes from “where is this file” to “which machine is this service running on, and who is managing it.”
  2. From “exists only when opened” to “always exists.” The service needs someone to keep it alive 24/7. This does not exist in VBA, because a file that is not open uses no resources.
  3. From “data lives with the code” to “data lives in the database.” Backup, restore, upgrade, and migration all revolve around the database, not around a file.

These three shifts map directly onto the four difficulties in your plan: what the monthly fee sells, how many centers one person can manage, how to calculate costs, and whether to keep the multi-entity goal. Once the mental model shifts, these four questions become much easier to answer.

KUDEA-H Web Version Business Plan: A Feasibility Review

This is a feasibility check of a business plan, not a technical review. The goal is to help you see what difficulties the plan will meet when it is put into practice, so that the plan itself stands on firmer ground.

The Most Important Point First

Code is not your risk. AI can write it. Your actual money and effort go elsewhere: deployment, security, backups, day-to-day operations, customer support. Whether a software business plan holds up depends mainly on whether it can serve dozens or hundreds of customers reliably over the long term, and whether it can pay for the person who maintains it.

Your VBA version already runs in two places and has received letters of interest. That is a successful project. The web version is one step forward from that base. The difficulties below do not reject your plan. They are questions the plan has to answer in order to hold up at the scale of 50 to 150 centers.

1. Four Difficulties the Plan Must Answer First

Difficulty 1: What the Monthly Fee Is Selling

You plan to charge monthly. The customer will ask: the software is installed on my own computer, why should I pay every month.

If the monthly fee sells the software itself, that question is hard to answer. If it sells ongoing service, such as installation, upgrades, backups, and someone to call when something breaks, then you have committed to long-term operations. Operations is the heaviest and most easily underestimated cost in this plan.

If this position is unclear, the revenue, staffing, and cost figures that follow cannot be calculated accurately. Please state first: does the monthly fee correspond to a software license, or to hosting plus support service.

Difficulty 2: Local Deployment Costs More to Operate Than VBA, and One Person Can Only Manage So Many Centers

You prioritize local deployment, with data never uploaded. That requirement is reasonable. But local deployment does not mean simple operations. A concrete comparison:

Operation VBA version Python web version
Backup Copy the Excel file Back up database, attachments, and configuration together, and make sure the three match
Restore Copy the file back Stop the service, restore the database and attachments, check configuration, restart, verify
Upgrade Send a new .xlsm file Pull code, install dependencies, run database migrations, restart, verify
Rollback Copy the old file back Roll back code, dependencies, and database structure together

VBA operations are file operations, and customers can learn them. Python web operations require understanding databases, dependencies, service processes, and migrations. That needs a dedicated person.

Your plan says INNSOC will provide one person. Please work out clearly: how many centers can this person manage at the same time. 10, 30, or 50. That number is the scale ceiling of the plan.

Difficulty 3: Operating Cost Grows With the Number of Centers, and Revenue May Not Keep Up

Your calculation is: 50 centers times a small monthly fee pays for one person. Under local deployment, the reality is:

  • Each center has its own separate system. Fixing one bug means connecting to 50 machines remotely and updating them one by one.
  • One remote troubleshooting session takes minutes to hours. Multiply by 50 centers and by how often it happens, and one person is quickly overwhelmed.
  • That person is busy with operations and has no time to develop the next version. This directly conflicts with your stated goal of using revenue to fund web version development.

The plan should state clearly: at 50 centers, what is the total monthly revenue. What does it cost per year to pay one person, including server, domain, and travel. In which month does revenue cover cost. If these numbers cannot be calculated, “revenue pays for the person” is only an assumption.

Difficulty 4: Local Deployment Means Giving Up Multi-Entity, and This Is an Explicit Trade-off

Your original proposal said that later you would switch to Postgres to support multi-entity access. But one program per center, with data not shared, means 50 to 150 centers are 50 to 150 separate systems, not one system that can scale. The multi-entity goal is in practice abandoned.

There are good reasons for this. Data security is simpler, and GDPR responsibility is simpler. But the plan should state this trade-off explicitly: what you are building is a software product serving many independent customers, not a platform. This will affect what funders and investors expect in terms of scalability.

2. Reminders Along the Way

  • Functional parity: VBA contains many practices that are not written down, such as how default values are filled, what basis reports use, and how abnormal data is handled. These are easily lost in a rewrite. Run the old and new systems in parallel at the two existing sites for a while before rolling out to interested customers.
  • Scaling upgrades and bug fixes: how to update one bug across 50 machines is a process question. The plan should reserve an approach, such as automatic updates or centralized hosting.
  • Data migration format differences: each center’s Excel may look different because of local changes. The migration script has to handle these differences. During the pilot period, try to keep the VBA data structure consistent.

3. If Scale Becomes Unmanageable Later: A Common Commercial Approach

Data not being uploaded is a reasonable requirement, and local deployment as the first choice is fine. But if local operations cannot support more than 100 centers, a common commercial approach is centralized hosting with tenant isolation, where each center’s data is strictly separated, plus a data processing agreement promising not to touch the data. This keeps data from mixing while also allowing scale.

Whether to take this path depends on whether the scale ceiling in Difficulty 2 actually becomes a bottleneck. There is no need to decide now, but it can be written into the plan as a future path.

4. Handle These After the Four Difficulties Have Answers

All of the following should wait until the four difficulties in Section 1 have conclusions. Discussing them now is premature.

  • Backup plus restore testing. Actually restore once on a regular schedule, and confirm the data is complete and the system runs. A backup that has never been tested is no backup.
  • One-command upgrade, with the ability to roll back to the previous version.
  • Monitoring and logs: is the service alive, and can errors be found.
  • Lean toward PaaS hosting, such as Render, Railway, or PythonAnywhere. They provide certificates, automatic deployment, managed backups, and one-click rollback, turning operations that need a technical person into a few clicks. The cost is higher fees and data stored with a third party.
  • Put server, domain, and labor hours into the budget.
  • Choose between Django and Flask. Django comes with an admin panel, authentication, permissions, and form validation, which is less work for a non-professional developer. Suggest the maintainer spend half a day going through the official Django tutorial before deciding.

Summary in One Paragraph

Whether the plan holds up depends mainly on four business questions:

  1. Does the monthly fee sell software or service.
  2. Under local deployment, how many centers can one person manage.
  3. Does the revenue from 50 centers cover the cost of the person and the infrastructure.
  4. Do you accept giving up multi-entity and building a software product for many independent customers.

If these four questions have answers, the plan stands. If they do not, problems will appear in operations and cost once scale grows. Everything else is execution detail, to be handled after these four are settled.
