Dos modelos mentales: VBA y Web

Un modelo mental es la imagen que tienes en la cabeza de “qué es este sistema”. Cuando surge un problema, la imagen que ves primero decide cómo tomas las decisiones. Muchas decisiones de tu plan de negocio se toman desde la imagen de VBA, y se desvían cuando se aplican a la web. A continuación se presentan las dos imágenes y, después, una comparación con afirmaciones concretas de tu plan.

1. El modelo mental de VBA

El sistema que tienes en la cabeza es un archivo de Excel.

  • Donde está el archivo, está el sistema. Si el archivo está en el ordenador de Zhang, el sistema está en el ordenador de Zhang.
  • Haz doble clic en el archivo y el sistema empieza a funcionar. Cierra el archivo y el sistema se detiene.
  • La interfaz (las hojas de cálculo), las reglas (las macros) y los datos (las celdas) viven todos dentro de este único archivo.
  • Para dárselo a otro centro, se copia el archivo. Las dos copias quedan entonces independientes y no se afectan entre sí.
  • Actualizar significa enviar un archivo nuevo, y el usuario sobrescribe el antiguo.
  • Hacer copia de seguridad significa copiar el archivo.
  • Si dos personas abren el mismo archivo al mismo tiempo, entran en conflicto. Por eso normalmente se turnan, o lo ponen en una unidad compartida y lo abren en momentos distintos.
  • Cuando algo va mal, se abre el archivo y se mira.

Esta imagen es simple y directa, y tu versión en VBA tuvo éxito siguiéndola.

2. El modelo mental de la Web (buenas prácticas)

El sistema que tienes en la cabeza debería ser un servicio que está siempre en funcionamiento, más una base de datos.

  • El servicio se ejecuta en una máquina que permanece encendida. El programa está siempre en ejecución, esperando que los usuarios accedan a él.
  • Un usuario abre una URL en el navegador, lo que significa acceder a este servicio. Cerrar el navegador no detiene el servicio.
  • Los datos viven en la base de datos, separados del programa del servicio. Cada vez que el programa hace algo, lee y escribe en la base de datos.
  • Que varios usuarios accedan al mismo tiempo es el estado normal. El programa debe atenderlos simultáneamente, y los datos de cada persona no deben interferir con los de los demás.
  • Actualizar significa reemplazar el programa en esa máquina. La próxima vez que los usuarios actualicen el navegador, verán la nueva versión, y los datos no se mueven.
  • Hacer copia de seguridad significa respaldar la base de datos y los archivos adjuntos, y asegurarse de que los registros de la base de datos coincidan con los archivos de la carpeta de adjuntos.
  • Cuando algo va mal, se miran los registros (logs) del servidor.
  • Alguien debe asegurarse siempre de que esa máquina permanezca encendida, de que el programa siga ejecutándose, de que la URL sea accesible y de que se hagan las copias de seguridad.

El punto clave de esta imagen: el sistema es algo que se ejecuta de forma continua, no un archivo que solo existe cuando se abre.

3. La misma pregunta, respondida por dos modelos mentales

Pregunta Modelo mental de VBA Modelo mental de la Web

Cuándo existe el sistema Cuando el archivo está abierto Todo el tiempo
Dónde están los datos En el archivo, junto con el código En la base de datos, separados del código
Cómo dárselo a otro centro Copiar el archivo Darles una URL y dejar que inicien sesión

Cómo hacer copia de seguridad Copiar el archivo Respaldar la base de datos y los adjuntos, mantenerlos coherentes

4. Qué afirmaciones de tu plan siguen usando el modelo mental de VBA

Algunas afirmaciones de tu plan necesitan una forma distinta de pensar al pasar a la web:

“Un programa para un centro, 50 programas 50 centros.”
Este es el pensamiento de copiar el archivo de VBA. En la web, 50 centros pueden ser 50 servicios separados, o 1 servicio gestionando 50 centros. Estos dos difieren mucho en carga de mantenimiento. Tu afirmación actual asume lo primero, pero tu plan no ha comparado los dos.

“En caso de necesidad nos conectaremos con la máquina remota.”
Este es el pensamiento de VBA de “ir a esa máquina y abrir el archivo”. En la web, la resolución de problemas suele empezar por los registros y la monitorización, e iniciar sesión en el servidor es el último recurso, no la práctica diaria.

“Los datos nunca se comparten entre distintos centros ni con nosotros por web.”
El requisito es razonable. Pero en el modelo mental de la web, se traduce en: los datos están en la base de datos del lado del servidor, cada centro solo puede ver sus propios datos, y tú como operador tampoco puedes verlos. Esa es una cuestión de aislamiento de inquilinos (tenant isolation), no una cuestión de “dónde se almacenan los datos”.

“La versión web es solo cambiar VBA por Python, la lógica no cambia.”
En el modelo mental de la web, la lógica de negocio va al programa del lado del servidor, los datos van a la base de datos y la interfaz va al navegador. Son tres piezas separadas, a diferencia de VBA, donde todo vive en un solo archivo.

5. Tres puntos concretos del cambio mental

  1. De “archivo” a “servicio”. La pregunta que haces a partir de ahora cambia de “dónde está este archivo” a “en qué máquina se ejecuta este servicio y quién lo gestiona”.
  2. De “solo existe cuando se abre” a “existe siempre”. El servicio necesita a alguien que lo mantenga vivo 24/7. Esto no existe en VBA, porque un archivo que no está abierto no consume recursos.
  3. De “los datos viven con el código” a “los datos viven en la base de datos”. La copia de seguridad, la restauración, la actualización y la migración giran todas en torno a la base de datos, no en torno a un archivo.

Estos tres cambios se corresponden directamente con las cuatro dificultades de tu plan: qué vende la cuota mensual, cuántos centros puede gestionar una persona, cómo calcular los costes y si mantener el objetivo multi-entidad. Una vez que el modelo mental cambia, estas cuatro preguntas se vuelven mucho más fáciles de responder.

Plan de negocio de la versión web de KUDEA-H: una revisión de viabilidad

Esta es una comprobación de viabilidad de un plan de negocio, no una revisión técnica. El objetivo es ayudarte a ver qué dificultades encontrará el plan cuando se ponga en práctica, para que el plan mismo se apoye en una base más firme.

Lo más importante, primero

El código no es tu riesgo. La IA puede escribirlo. Tu dinero y tu esfuerzo reales van a otro sitio: el despliegue, la seguridad, las copias de seguridad, las operaciones diarias, la atención al cliente. Que un plan de negocio de software se sostenga depende principalmente de si puede servir de forma fiable a decenas o cientos de clientes a largo plazo, y de si puede pagar a la persona que lo mantiene.

Tu versión en VBA ya funciona en dos lugares y ha recibido cartas de interés. Eso es un proyecto exitoso. La versión web es un paso adelante desde esa base. Las dificultades siguientes no rechazan tu plan. Son preguntas que el plan tiene que responder para sostenerse a la escala de 50 a 150 centros.

1. Cuatro dificultades que el plan debe responder primero

Dificultad 1: Qué vende la cuota mensual

Planeas cobrar mensualmente. El cliente preguntará: el software está instalado en mi propio ordenador, por qué debería pagar cada mes.

Si la cuota mensual vende el software en sí, esa pregunta es difícil de responder. Si vende un servicio continuo, como instalación, actualizaciones, copias de seguridad y alguien a quien llamar cuando algo se rompe, entonces te has comprometido a una operación a largo plazo. La operación es el coste más pesado y más fácilmente subestimado de este plan.

Si esta posición no está clara, las cifras de ingresos, personal y costes que siguen no pueden calcularse con precisión. Por favor, indica primero: ¿la cuota mensual corresponde a una licencia de software, o a alojamiento más servicio de soporte?

Dificultad 2: El despliegue local cuesta más de operar que VBA, y una persona solo puede gestionar un número limitado de centros

Priorizas el despliegue local, con los datos nunca subidos. Ese requisito es razonable. Pero el despliegue local no significa operaciones simples. Una comparación concreta:

Operación Versión VBA Versión web en Python
Copia de seguridad Copiar el archivo de Excel Respaldar la base de datos, los adjuntos y la configuración juntos, y asegurarse de que los tres coincidan
Restauración Copiar el archivo de vuelta Detener el servicio, restaurar la base de datos y los adjuntos, comprobar la configuración, reiniciar, verificar
Actualización Enviar un nuevo archivo .xlsm Traer el código, instalar dependencias, ejecutar migraciones de la base de datos, reiniciar, verificar
Reversión Copiar el archivo antiguo de vuelta Revertir el código, las dependencias y la estructura de la base de datos juntos

Las operaciones de VBA son operaciones de archivos, y los clientes pueden aprenderlas. Las operaciones web en Python requieren entender bases de datos, dependencias, procesos de servicio y migraciones. Eso necesita una persona dedicada.

Tu plan dice que INNSOC proporcionará una persona. Por favor, calcula claramente: cuántos centros puede gestionar esta persona al mismo tiempo. 10, 30 o 50. Ese número es el techo de escala del plan.

Dificultad 3: El coste operativo crece con el número de centros, y los ingresos pueden no seguir el ritmo

Tu cálculo es: 50 centros multiplicados por una pequeña cuota mensual pagan a una persona. Bajo el despliegue local, la realidad es:

  • Cada centro tiene su propio sistema separado. Arreglar un error significa conectarse remotamente a 50 máquinas y actualizarlas una por una.
  • Una sesión de resolución remota de problemas lleva de minutos a horas. Multiplícalo por 50 centros y por la frecuencia con que ocurre, y una persona se ve rápidamente desbordada.
  • Esa persona está ocupada con las operaciones y no tiene tiempo para desarrollar la siguiente versión. Esto entra directamente en conflicto con tu objetivo declarado de usar los ingresos para financiar el desarrollo de la versión web.

El plan debería indicar claramente: a 50 centros, cuál es el ingreso mensual total. Cuánto cuesta al año pagar a una persona, incluidos servidor, dominio y viajes. En qué mes los ingresos cubren el coste. Si estas cifras no pueden calcularse, “los ingresos pagan a la persona” es solo una suposición.

Dificultad 4: El despliegue local significa renunciar a multi-entidad, y esto es un compromiso explícito

Tu propuesta original decía que más adelante cambiarías a Postgres para soportar acceso multi-entidad. Pero un programa por centro, con datos no compartidos, significa que 50 a 150 centros son 50 a 150 sistemas separados, no un sistema que pueda escalar. El objetivo multi-entidad se abandona en la práctica.

Hay buenas razones para ello. La seguridad de los datos es más simple, y la responsabilidad del RGPD es más simple. Pero el plan debería indicar este compromiso explícitamente: lo que estás construyendo es un producto de software que sirve a muchos clientes independientes, no una plataforma. Esto afectará a lo que los financiadores e inversores esperan en términos de escalabilidad.

2. Recordatorios a lo largo del camino

  • Paridad funcional: VBA contiene muchas prácticas que no están escritas, como cómo se rellenan los valores por defecto, en qué se basan los informes y cómo se manejan los datos anómalos. Estas se pierden fácilmente en una reescritura. Ejecuta los sistemas antiguo y nuevo en paralelo en los dos sitios existentes durante un tiempo antes de desplegar a los clientes interesados.
  • Actualizaciones de escala y corrección de errores: cómo actualizar un error en 50 máquinas es una cuestión de proceso. El plan debería reservar un enfoque, como actualizaciones automáticas o alojamiento centralizado.
  • Diferencias de formato en la migración de datos: el Excel de cada centro puede verse distinto debido a cambios locales. El script de migración tiene que manejar estas diferencias. Durante el periodo piloto, intenta mantener coherente la estructura de datos de VBA.

3. Si la escala se vuelve inmanejable más adelante: un enfoque comercial común

Que los datos no se suban es un requisito razonable, y el despliegue local como primera opción está bien. Pero si las operaciones locales no pueden soportar más de 100 centros, un enfoque comercial común es el alojamiento centralizado con aislamiento de inquilinos, donde los datos de cada centro están estrictamente separados, más un acuerdo de procesamiento de datos que prometa no tocar los datos. Esto evita que los datos se mezclen y al mismo tiempo permite escalar.

Si tomar este camino depende de si el techo de escala de la Dificultad 2 se convierte realmente en un cuello de botella. No hay necesidad de decidirlo ahora, pero puede escribirse en el plan como un camino futuro.

4. Abordar esto después de que las cuatro dificultades tengan respuesta

Todo lo siguiente debería esperar hasta que las cuatro dificultades de la Sección 1 tengan conclusiones. Discutirlo ahora es prematuro.

  • Copia de seguridad más prueba de restauración. Restaura de verdad una vez de forma periódica, y confirma que los datos están completos y el sistema funciona. Una copia de seguridad que nunca se ha probado no es una copia de seguridad.
  • Actualización con un solo comando, con la capacidad de revertir a la versión anterior.
  • Monitorización y registros: ¿está vivo el servicio y pueden encontrarse los errores?
  • Inclinarse por el alojamiento PaaS, como Render, Railway o PythonAnywhere. Proporcionan certificados, despliegue automático, copias de seguridad gestionadas y reversión con un clic, convirtiendo operaciones que necesitan a una persona técnica en unos pocos clics. El coste es tarifas más altas y datos almacenados con un tercero.
  • Incluir el servidor, el dominio y las horas de trabajo en el presupuesto.
  • Elegir entre Django y Flask. Django viene con un panel de administración, autenticación, permisos y validación de formularios, lo que es menos trabajo para un desarrollador no profesional. Sugiere que el mantenedor dedique medio día a seguir el tutorial oficial de Django antes de decidir.

Resumen en un párrafo

Que el plan se sostenga depende principalmente de cuatro cuestiones de negocio:

  1. Si la cuota mensual vende software o servicio.
  2. Bajo el despliegue local, cuántos centros puede gestionar una persona.
  3. Si los ingresos de 50 centros cubren el coste de la persona y la infraestructura.
  4. Si aceptas renunciar a multi-entidad y construir un producto de software para muchos clientes independientes.

Si estas cuatro preguntas tienen respuesta, el plan se sostiene. Si no las tienen, aparecerán problemas en las operaciones y los costes cuando la escala crezca. Todo lo demás son detalles de ejecución, que deben abordarse después de que estas cuatro estén resueltas.
