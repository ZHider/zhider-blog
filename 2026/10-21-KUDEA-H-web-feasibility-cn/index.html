KUDEA-H Web 版商业企划：可行性审视

中文
English
Euskara

这是一份商业企划的可行性检查，不是技术评审。目的是帮你看清企划落地时会遇到什么困难，让企划本身更站得住。

先说最要紧的

代码本身不是你的风险，AI 能写出来。你实际要花的钱和精力在别处：部署、安全、备份、日常运维、客户支持。一份软件企划能不能成立，主要看能不能长期稳定地服务几十上百个客户，并且养得起维护它的人。

你的 VBA 版已经在两处运行，还收到了意向书，这是一个成功的项目。Web 版是在这个基础上往前走一步。下面这些困难不是否定你的企划，而是企划要能回答它们，才撑得住 50 到 150 个中心的规模。

一、企划必须先回答的四个困难

困难 1：月费卖的是什么

你打算按月收费。客户会问，软件装在我自己的电脑上，我为什么每个月都要付钱。

如果月费卖的是软件本身，这个问题很难回答。如果卖的是持续的服务，比如安装、升级、备份、出问题时有人管，那你就承诺了长期运维。而运维是这份企划里最重、最容易被低估的成本。

这个定位不清楚，后面的收入、人力、成本都算不准。请先写明：月费对应的是软件许可，还是托管加支持服务。

困难 2：本地部署的运维比 VBA 重，一个人能管几个中心

你优先选本地部署，数据不上传，这个诉求合理。但本地部署不等于运维简单。具体对比一下：

操作 VBA 版 Python Web 版
备份 拷贝 Excel 文件 数据库、附件、配置要一起备份，还要保证三者对得上
恢复 把文件拷回去 停服务、还原数据库和附件、检查配置、重启、验证
升级 传一个新的 .xlsm 文件 拉代码、装依赖、跑数据库迁移、重启、验证
回滚 拷回旧文件 代码、依赖、数据库结构要一起退回

VBA 的运维是文件操作，客户自己学得会。Python Web 的运维要懂数据库、依赖、服务进程、迁移，需要专门的人。

你的企划里写的是 INNSOC 出一个人。请算清楚：这个人同时能管几个中心。10 个，30 个，还是 50 个。这个数字就是企划的规模上限。

困难 3：运维成本随中心数增长，收入未必跟得上

你的算法是 50 个中心乘以小额月费，就能养一个人。按本地部署算，实际情况是：

  • 每个中心一套独立系统。修一个 bug，要远程连 50 台机器逐个更新。
  • 远程排障一次要几分钟到几小时。乘上 50 个中心和发生频率，一个人很快忙不过来。
  • 这个人忙着运维，就没时间开发下一版。这和你说的用收入养 Web 版开发，正好冲突。

企划里要写清楚：50 个中心时，月费总收入是多少。养一个人一年要多少钱，含服务器、域名、差旅。盈亏平衡点在哪个月。这几笔账算不出来，用收入养人就只是一个假设。

困难 4：本地部署等于放弃多实体，这是一个明确取舍

你最初的方案写了，以后换 Postgres 支持多实体访问。但一个中心一套程序、数据不共享，意味着 50 到 150 个中心是 50 到 150 套独立系统，不是一个能扩展的系统。多实体这个目标实际上放弃了。

这样做有它的道理，数据安全简单，GDPR 责任也简单。但企划里要写明这个取舍：你做的是服务多个独立客户的软件产品，不是一个平台。这会影响到资助方和投资人对可扩展性的期待。

二、过程中的提醒

  • 功能对等：VBA 里有不少文档没写的做法，比如默认值怎么填、报表按什么口径、异常数据怎么处理。重写时容易丢。先在现有两处并行跑一段时间，再推给意向客户。
  • 升级和 bug 修复的规模化：50 台机器怎么更新一个 bug，这是流程问题。企划里要预留方案，比如自动更新，或者集中托管。
  • 数据迁移格式差异：各中心的 Excel 可能因为本地改动长得不一样。迁移脚本要能吃下这些差异。试点期尽量统一 VBA 的数据结构。

三、如果以后规模撑不住：可参考的商业做法

数据不上传是合理的诉求，本地部署作为首选没有问题。但如果本地运维撑不住 100 个以上的中心，常见的商业做法是集中托管加租户隔离，每个中心的数据严格分开，再签数据处理协议承诺不接触数据。这样既能保证数据不串，也能规模化。

要不要走这条路，取决于困难 2 的规模上限是否真的成了瓶颈。现在不用决定，但可以写进企划的未来路径里。

四、四个困难有答案之后，再处理这些

以下各项都要等第一节的四个困难有结论之后再说，现在讨论偏早。

  • 备份加恢复测试。定期真的还原一次，确认数据完整、系统能跑。没测过的备份等于没有备份。
  • 一条命令升级，能回滚到上一个版本。
  • 监控和日志，服务活着没有，出错能不能查到。
  • 托管倾向选 PaaS，比如 Render、Railway、PythonAnywhere。它们带证书、自动部署、托管备份、一键回滚，把需要技术人员做的操作变成点几下按钮。代价是费用高一些，数据放在第三方。
  • 把服务器、域名、人力工时写进预算。
  • Django 和 Flask 二选一。Django 自带后台管理、认证、权限、表单校验，对非专业开发者更省事。建议维护者花半天走一遍 Django 官方教程再决定。

一句话总结

企划能不能成立，主要看四个商业问题：

  1. 月费卖的是软件还是服务。
  2. 本地部署下，一个人能管几个中心。
  3. 50 个中心的收入，够不够覆盖人和基础设施的成本。
  4. 你是否接受放弃多实体，做多个独立客户的软件产品。

这四个问题有答案，企划就站得住。答不上来，规模一大就会在运维和成本上出问题。其余都是执行细节，等这四个问题定了再说。

两种心智模型：VBA 和 Web

心智模型就是你脑子里“这个系统是什么”的画面。遇到问题时，你脑子里先浮现什么，决定了你怎么做决定。你现在的企划里有很多决定，是按 VBA 的画面做出来的，放到 Web 上会走偏。下面把两个画面摆出来，再对照你企划里的具体说法。

一、VBA 的心智模型

你脑子里的系统是一个 Excel 文件。

  • 文件在哪里，系统就在哪里。文件在张三的电脑上，系统就在张三的电脑上。
  • 双击打开文件，系统开始工作。关掉文件，系统就停了。
  • 界面（工作表）、规则（宏）、数据（单元格），三样东西都装在这一个文件里。
  • 想给另一个中心用，就复制一份文件过去。两份文件从此各自独立，互不影响。
  • 升级就是发一个新文件，用户覆盖旧的。
  • 备份就是复制这个文件。
  • 两个人同时打开同一个文件会冲突，所以一般是轮流用，或者放在共享盘上大家错开时间开。
  • 出问题，就打开那个文件看。

这个画面简单、直接，而且你的 VBA 版就是按这个画面做成功的。

二、Web 的心智模型（最佳实践）

你脑子里的系统应该是一个一直在运行的服务，加一个数据库。

  • 服务放在一台一直开着的机器上。程序一直在跑，等着用户来访问。
  • 用户用浏览器打开一个网址，就是在访问这个服务。关掉浏览器，服务还在跑。
  • 数据放在数据库里，和服务程序分开放。程序每次办事，都去数据库读数据、写数据。
  • 多个用户同时访问是正常状态。程序要能同时处理，各人的数据互不干扰。
  • 升级是在那台机器上换程序。用户下次刷新浏览器，看到的就是新版本，数据不用动。
  • 备份是备份数据库和附件，而且要保证数据库里的记录和附件文件夹里的文件对得上。
  • 出问题，看服务器上的日志。
  • 必须一直有人保证那台机器开着、程序在跑、网址能访问、备份在做。

这个画面的重点是：系统是一个持续运行的东西，不是一个打开才存在的文件。

三、同一个问题，两种心智怎么回答

问题 VBA 心智 Web 心智
系统在哪里 在一个文件里 在一台一直开着的机器上
系统什么时候存在 文件打开时 一直存在
数据在哪里 在文件里，和代码在一起 在数据库里，和代码分开
怎么给另一个中心用 复制一份文件 给一个网址，让他们登录
怎么升级 发一个新文件 在服务器上换程序，用户刷新就生效
怎么备份 复制文件 备份数据库和附件，保证两者对得上
几个人能同时用 一个，或者轮流 设计上就是多人同时
出问题找谁 用的人自己看文件 需要有人管服务器和程序
谁来维护 用的人自己管自己的文件 需要有专门的人管服务器

四、你企划里哪些说法还是 VBA 心智

你企划里有几个说法，放到 Web 上需要换一种想法：

“One program for one center，50 programs 50 centers”
这是 VBA 的复制文件思路。在 Web 里，50 个中心可以是 50 个独立的服务，也可以是 1 个服务管 50 个中心。这两种在运维工作量上差很多。你现在的说法默认了前者，但企划里没有比较过两者。

“In case of need we will connect with the remote machine”
这是 VBA 的“去那台机器上打开文件”思路。在 Web 里，排障一般先看日志、看监控，必要时再登录服务器。远程连机器是最后手段，不是日常做法。

“Data is never shared between different centers neither to us by web”
这个诉求合理。但在 Web 心智里，它要翻译成：数据放在服务端的数据库里，每个中心只能看到自己的数据，你作为运营方也看不到。这是租户隔离问题，不是“数据放在哪里”问题。

“Web 版就是把 VBA 换成 Python，逻辑不变”
在 Web 心智里，业务逻辑要放到服务端程序里，数据要放到数据库里，界面要放到浏览器里。这是三块东西，不像 VBA 那样装在一个文件里。

五、心智转变的三个具体点

  1. 从“文件”转到“服务”：你以后要问的问题，从“这个文件在哪”变成“这个服务在哪台机器上跑，谁在管它”。
  2. 从“打开才存在”转到“一直存在”：服务需要 7×24 小时有人保证它活着。这在 VBA 里不存在，因为文件不开就不占任何资源。
  3. 从“数据跟代码在一起”转到“数据在数据库里”：备份、恢复、升级、迁移，全部围绕数据库来做，不再围绕文件来做。

这三个转变，直接对应你企划里那四个困难：月费卖什么、一个人管几个中心、成本怎么算、多实体要不要。心智换过来了，这四个问题会变得好回答很多。
