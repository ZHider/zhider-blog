两种心智模型：VBA 与 Web

心智模型是你脑子里对”这个系统是什么”的画面。当问题出现时，你最先看到的那个画面决定了你如何做决策。你商业计划里的许多决策是从 VBA 的画面出发做出的，一旦套用到 Web 上就会跑偏。下面先讲这两个画面，再对照你计划中的具体表述进行比较。

1. VBA 心智模型

你脑子里的系统是一个 Excel 文件。

  • 文件在哪里，系统就在哪里。文件在张三的电脑上，系统就在张三的电脑上。
  • 双击文件，系统开始工作。关闭文件，系统就停止。
  • 界面（工作表）、规则（宏）和数据（单元格）全都住在这一个文件里。
  • 要交给另一个中心，就把文件复制过去。两份副本从此互相独立，互不影响。
  • 升级就是发一个新文件，用户覆盖旧的。
  • 备份就是复制文件。
  • 如果两个人同时打开同一个文件，就会冲突。所以通常大家轮流用，或者放到共享盘上错开时间打开。
  • 出了问题，打开文件看一看。

这个画面简单直接，你的 VBA 版本就是照着它做成功的。

2. Web 心智模型（最佳实践）

你脑子里的系统应该是一个一直在运行的服务，外加一个数据库。

  • 服务运行在一台一直开着的机器上。程序一直在跑，等着用户来访问。
  • 用户在浏览器里打开一个网址，就是访问这个服务。关掉浏览器不会让服务停止。
  • 数据住在数据库里，和服务程序分开。程序每做一件事，都要读写数据库。
  • 多个用户同时访问是正常状态。程序必须同时处理他们，每个人的数据不能互相干扰。
  • 升级就是替换那台机器上的程序。用户下次刷新浏览器就能看到新版本，数据不动。
  • 备份就是备份数据库和附件，并确保数据库里的记录和附件文件夹里的文件对得上。
  • 出了问题，看服务器上的日志。
  • 必须始终有人保证那台机器开着、程序在跑、网址能访问、备份在做。

这个画面的关键点：系统是一个持续运行的东西，而不是一个只有打开时才存在的文件。

3. 同一个问题，两种心智模型的回答

问题 VBA 心智模型 Web 心智模型
系统在哪里 在一个文件里 在一台一直开着的机器上
系统何时存在 文件打开时 一直存在
数据在哪里 在文件里，和代码在一起 在数据库里，和代码分开
如何交给另一个中心 复制文件 给他们一个网址，让他们登录
如何升级 发一个新文件 替换服务器上的程序，用户刷新就能看到
如何备份 复制文件 备份数据库和附件，保持两者一致
多少人能同时用 一个，或者轮流 为多人同时使用而设计
出问题找谁 用户打开文件自己看 得有人管理服务器和程序
谁来维护 每个用户管自己的文件 得有专人管理服务器

4. 你计划中哪些表述仍在用 VBA 心智模型

你计划里有几处表述在搬到 Web 上时需要换一种思路：

“一个中心一个程序，50 个程序 50 个中心。”
这是 VBA 的复制文件思维。在 Web 上，50 个中心可以是 50 个独立服务，也可以是 1 个服务管理 50 个中心。这两者在维护工作量上差别很大。你现在的表述假设的是前者，但你的计划并没有比较过两者。

“如有需要，我们会连接远程机器。”
这是 VBA 的”去那台机器上打开文件”思维。在 Web 上，排查问题通常从日志和监控开始，登录服务器是最后手段，而不是日常做法。

“不同中心之间、以及通过 Web 向我们，数据绝不共享。”
这个要求是合理的。但在 Web 心智模型里，它翻译成：数据放在服务端数据库里，每个中心只能看到自己的数据，你作为运营方也看不到。这是一个租户隔离问题，而不是”数据存在哪里”的问题。

“Web 版就是把 VBA 换成 Python，逻辑不变。”
在 Web 心智模型里，业务逻辑进服务端程序，数据进数据库，界面进浏览器。这是三个分开的部分，不像 VBA 那样全都住在一个文件里。

5. 心智转变的三个具体要点

  1. 从”文件”到”服务”。 你今后要问的问题，从”这个文件在哪里”变成”这个服务跑在哪台机器上，谁在管它”。
  2. 从”打开才存在”到”一直存在”。 服务需要有人 7×24 小时让它活着。这在 VBA 里是不存在的，因为没打开的文件不占资源。
  3. 从”数据和代码住在一起”到”数据住在数据库里”。 备份、恢复、升级、迁移全都围绕数据库转，而不是围绕一个文件转。

这三个转变直接对应你计划里的四个难点：月费卖的是什么、一个人能管多少个中心、成本怎么算、要不要保留多实体目标。心智模型一旦转变，这四个问题就变得容易回答多了。

KUDEA-H Web 版商业计划：可行性评审

这是对一份商业计划的可行性检查，不是技术评审。目的是帮你看到计划落地时会遇到哪些困难，让计划本身站得更稳。

最重要的一点先说

代码不是你的风险，AI 可以写。你真正的钱和精力花在别处：部署、安全、备份、日常运维、客户支持。一个软件商业计划能不能成立，主要看它能否长期可靠地服务几十到几百个客户，以及能否养得起维护它的那个人。

你的 VBA 版本已经在两个地方运行，并收到了意向函。那是一个成功的项目。Web 版是在这个基础上往前走一步。下面的困难不是否定你的计划，而是计划要在 50 到 150 个中心的规模上站住脚，必须回答的问题。

1. 计划必须先回答的四个难点

难点 1：月费卖的是什么

你打算按月收费。客户会问：软件装在我自己的电脑上，我为什么要每个月付钱。

如果月费卖的是软件本身，这个问题很难回答。如果卖的是持续服务，比如安装、升级、备份、出问题有人可找，那你就承诺了长期运维。运维是这个计划里最重、也最容易被低估的成本。

如果这个定位不清楚，后面的收入、人员、成本数字都算不准。请先说明：月费对应的是软件许可，还是托管加支持服务。

难点 2：本地部署的运维比 VBA 更重，一个人能管的中心数量有限

你优先选择本地部署，数据永不上传。这个要求是合理的。但本地部署不等于运维简单。具体对比一下：

操作 VBA 版 Python Web 版
备份 复制 Excel 文件 数据库、附件、配置一起备份，并确保三者对得上
恢复 把文件复制回来 停服务，恢复数据库和附件，检查配置，重启，验证
升级 发一个新的 .xlsm 文件 拉代码、装依赖、跑数据库迁移、重启、验证
回滚 把旧文件复制回来 代码、依赖、数据库结构一起回滚

VBA 的运维是文件操作，客户可以学会。Python Web 的运维需要懂数据库、依赖、服务进程和迁移。这需要专人。

你的计划说 INNSOC 会提供一个人。请算清楚：这个人同时能管多少个中心。10 个、30 个还是 50 个。这个数字就是计划的规模天花板。

难点 3：运营成本随中心数量增长，收入可能跟不上

你的算法是：50 个中心乘以一笔小月费，养一个人。在本地部署下，现实是：

  • 每个中心都是各自独立的系统。修一个 bug 意味着远程连接 50 台机器，一台一台更新。
  • 一次远程排障要几分钟到几小时。乘以 50 个中心，再乘以发生频率，一个人很快就会被淹没。
  • 这个人忙于运维，就没时间开发下一个版本。这和你说的”用收入养 Web 版开发”的目标直接冲突。

计划应该写清楚：50 个中心时，每月总收入是多少。养一个人一年要花多少钱，包括服务器、域名和差旅。哪个月收入能覆盖成本。如果这些数字算不出来，”收入养人”就只是一个假设。

难点 4：本地部署意味着放弃多实体，这是一个明确的取舍

你最初的提案说，以后会换成 Postgres 来支持多实体访问。但一个中心一个程序、数据不共享，意味着 50 到 150 个中心就是 50 到 150 个独立系统，而不是一个可扩展的系统。多实体目标实际上被放弃了。

这有充分的理由。数据安全更简单，GDPR 责任更简单。但计划应该明确写出这个取舍：你建的是一个服务众多独立客户的软件产品，而不是一个平台。这会影响资助方和投资人对可扩展性的预期。

2. 沿途提醒

  • 功能对等：VBA 里包含许多没有写下来的做法，比如默认值怎么填、报表依据什么、异常数据怎么处理。这些在重写中很容易丢失。在推广给意向客户之前，先在现有两个站点让新旧系统并行运行一段时间。
  • 规模化的升级与 bug 修复：一个 bug 怎么在 50 台机器上更新，是一个流程问题。计划应该预留一个方案，比如自动更新或集中托管。
  • 数据迁移的格式差异：每个中心的 Excel 可能因为本地改动而长得不一样。迁移脚本必须处理这些差异。试点期间，尽量保持 VBA 数据结构一致。

3. 如果以后规模管不过来：一种常见的商业做法

数据不上传是合理要求，本地部署作为首选也没问题。但如果本地运维支撑不了 100 个以上的中心，一种常见的商业做法是集中托管加租户隔离，每个中心的数据严格分开，再加一份承诺不碰数据的DPA。这样既不让数据混在一起，又能上规模。

要不要走这条路，取决于难点 2 里的规模天花板是否真的成为瓶颈。现在不必决定，但可以写进计划，作为未来路径。

4. 四个难点有答案之后再处理这些

以下所有事项都应等第 1 节的四个难点有结论之后再谈。现在讨论为时过早。

  • 备份加恢复测试。定期真正恢复一次，确认数据完整、系统能跑。没测过的备份不算备份。
  • 一键升级，并且能回滚到上一个版本。
  • 监控和日志：服务是否活着，错误能否被发现。
  • 倾向 PaaS 托管，比如 Render、Railway 或 PythonAnywhere。它们提供证书、自动部署、托管备份和一键回滚，把需要技术人员才能做的运维变成点几下鼠标。代价是费用更高，数据存在第三方那里。
  • 把服务器、域名和工时放进预算。
  • 在 Django 和 Flask 之间做选择。Django 自带管理后台、认证、权限和表单验证，对非专业开发者来说工作量更小。建议维护者花半天过一遍 Django 官方教程再决定。

一段话总结

计划能不能成立，主要取决于四个商业问题：

  1. 月费卖的是软件还是服务。
  2. 本地部署下，一个人能管多少个中心。
  3. 50 个中心的收入能否覆盖这个人和基础设施的成本。
  4. 你是否接受放弃多实体，做一个服务众多独立客户的软件产品。

这四个问题有答案，计划就站得住。没有答案，规模一上来，运维和成本就会出问题。其他一切都是执行细节，等这四个问题定了再处理。
